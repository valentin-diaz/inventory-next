# El frontend tiene su base: cliente de la API, manejo de errores, textos en español y shadcn

## Context

Hoy el frontend es un `create-next-app` casi vacío:

- **`app/layout.tsx`:**
  - Carga las fuentes Geist.
  - Declara `<html lang="en">`.
  - Tiene la `metadata` de la plantilla ("Create Next App").
- **`app/page.tsx`:**
  - Muestra el título "Store Chain Simulator".
  - Importa `Image` de `next/image` sin usarlo.
- **`app/globals.css`:** los tokens de color de la plantilla y un `body` con Arial.
- **`next.config.ts`:**
  - Tiene `cacheComponents: true` y `partialPrefetching: true`.
  - Procesa Tailwind con una regla de Turbopack (`@tailwindcss/turbopack`). No hay `postcss.config`.
- **`.gitignore`:** ignora `.env*`.
- **`package.json`:** solo tiene `next`, `react` y `react-dom`, más las herramientas de la plantilla.
- **`eslint.config.mjs`:** ignora `.next/`, `out/`, `build/` y `next-env.d.ts`.
- **`public/`:** las cinco imágenes de la plantilla (`file.svg`, `globe.svg`, `next.svg`, `vercel.svg`, `window.svg`), que nadie usa.

La API de Django (`../../inventario`) ya está terminada. Lo que importa de ella para esta fase:

- **`GET /api/health/`** (`core/views.py`, `HealthCheckView`):
  - No pide autenticación.
  - Responde `200 {"status": "ok", "database": "ok"}`.
  - Si su `SELECT 1` contra la base de datos falla, responde `503 {"status": "error", "database": "unavailable"}`.
- **Errores de DRF**, con tres formas:
  - `{"detail": "…"}` para permisos, "no encontrado" y similares.
  - `{"<campo>": ["…"]}` para validación.
  - `{"non_field_errors": ["…"]}` para validaciones que no son de un campo.

  El valor de un campo puede ser una **lista** o un **string**. `validate()` corre dentro de `is_valid()`, que pasa por `as_serializer_error` y envuelve cada string en una lista. Un `ValidationError` lanzado en `create()` corre dentro de `save()`, nadie lo envuelve, y llega como string. Así pasa con `{"quantity": "Not enough stock: …"}` en `inventory/serializers.py`.
- **Listas paginadas** (`core/pagination.py`, `PageNumberPagination`): `{count, next, previous, results}`.
- **Códigos, no nombres:**
  - regiones: 16 códigos ISO sin el prefijo `CL-`, en `stores/models.py`;
  - estados de tienda: `open`, `temporarily_closed`, `closed`;
  - tipos de movimiento: `opening`, `purchase`, `sale`, `adjustment`;
  - roles: `seller`, `manager`, más `superadmin` desde `role_of`.
- **Precios:** son `DecimalField`, y DRF los manda como string (`"12990.00"`).

**Qué falta.** Todas las fases siguientes llaman a la API de la misma forma y arman sus pantallas con los mismos componentes. Antes de construir la primera pantalla real hacen falta:

- la URL de la API configurada;
- los tipos generados desde el schema;
- un cliente tipado y solo de servidor;
- dos helpers que conviertan las respuestas de error de la API en lo que ve el usuario;
- las funciones de formato y los nombres en español;
- los componentes de shadcn;
- una página que pruebe que todo conecta.

**La idea clave.** El navegador nunca habla con Django: lo hace el servidor de Next.js, con un cliente que se crea **por request** y que no puede importarse desde el navegador. Cada falla se trata según su tipo:

- **Lo que se espera** se **devuelve como valor**: un 403, un 400 con errores de validación, la API caída en la página de inicio. La página o el formulario lo muestran en su lugar.
- **Lo que no se espera** se **lanza**, y lo atrapa un error boundary: un bug, una variable de entorno que falta.

## Approach

Nueve pasos, cada uno es un commit:

1. Configuración (`API_URL`).
2. Tipos generados desde el schema.
3. Cliente de la API y `Paginated<T>`.
4. shadcn.
5. Layout en español.
6. Formato y nombres en español.
7. Helpers de errores.
8. Página de inicio como smoke test.
9. README.

El orden sigue las dependencias:

- el cliente necesita los tipos, y los tipos necesitan la API corriendo;
- `labels.ts` usa los enums de los tipos generados;
- el layout monta el `<Toaster />` que agrega shadcn;
- `<PermissionDenied />` usa la `Card` de shadcn;
- la página de inicio usa el cliente y los tokens de color de shadcn.

### Step 1 — Configurar `API_URL` y versionar `.env.example`

La app necesita saber dónde está la API, y cada desarrollador tiene que poder configurarlo sin tocar código. Next.js carga `.env.local` en `process.env`. Una variable **sin** el prefijo `NEXT_PUBLIC_` existe solo en el servidor: en el código que llega al navegador, Next.js la reemplaza por un string vacío ([Environment Variables](https://nextjs.org/docs/app/guides/environment-variables); local: `node_modules/next/dist/docs/01-app/02-guides/environment-variables.md`). Eso es justo lo que queremos, porque solo el servidor de Next.js habla con Django.

`.env.local` no se commitea, así que hace falta un `.env.example` que diga qué variables existen. El problema es que `.gitignore` tiene `.env*`, y `*` calza con cualquier cosa salvo `/`, así que también ignora `.env.example`.

**What we'll implement:**
- Agregar `!.env.example` a `.gitignore`, **debajo** de `.env*`.
- Crear `.env.example` con `API_URL=http://localhost:8000`.
- Crear `.env.local` como copia de `.env.example`. No se commitea.

`.gitignore`
```diff
 # env files (can opt-in for committing if needed)
 .env*
+!.env.example
```

`.env.example` (nuevo)
```diff
+# Base URL of the Inventario API.
+# Server-only: it has no NEXT_PUBLIC_ prefix, so it never reaches the browser.
+API_URL=http://localhost:8000
```

```bash
cp .env.example .env.local
```

Fíjate en dos cosas:

- **El orden importa.** Cuando varios patrones calzan con el mismo archivo, *"the last matching pattern decides the outcome"* ([gitignore — DESCRIPTION](https://git-scm.com/docs/gitignore#_description)). Si `!.env.example` estuviera antes de `.env*`, `.env*` lo volvería a ignorar.
- **El camino que se descartó** es reemplazar `.env*` por una lista (`.env`, `.env.local`…). Cada nombre nuevo, como `.env.production.local`, habría que acordarse de agregarlo, y el día que alguien lo olvide se commitea un secreto. `.env*` más una excepción cubre también los nombres que todavía no existen.

**Verify:**
- `git status` muestra `.env.example` como archivo nuevo y no muestra `.env.local`.
- `git check-ignore -v .env.local` imprime la regla `.env*`.
- `git check-ignore .env.example` no imprime nada.

**Suggested commit name:** `chore: add .env.example with API_URL`

### Step 2 — Generar los tipos de la API

`openapi-fetch`, en el paso siguiente, valida rutas, parámetros, cuerpos y respuestas contra un archivo de tipos. Ese archivo lo genera `openapi-typescript` a partir del schema OpenAPI de la API (`/api/schema/`, en YAML). Sin el script, cada vez que cambie la API alguien tendría que recordar el comando completo.

`openapi-typescript` solo corre cuando alguien ejecuta el script, nunca mientras la app atiende requests. Por eso va en `devDependencies`, que es para lo que solo se necesita mientras se desarrolla ([npm — package.json, devDependencies](https://docs.npmjs.com/cli/v10/configuring-npm/package-json#devdependencies)).

**What we'll implement:**
- Instalar `openapi-typescript` como dependencia de desarrollo.
- Agregar el script `api:types` a `package.json`. Genera `lib/api/schema.d.ts` desde `http://localhost:8000/api/schema/`.
- Generar `lib/api/schema.d.ts` con la API corriendo, y commitearlo.
- Agregar `lib/api/schema.d.ts` a `globalIgnores` en `eslint.config.mjs`.

```bash
npm install -D openapi-typescript
npm run api:types   # con la API corriendo en localhost:8000
```

`package.json`
```diff
   "scripts": {

     "start": "next start",
-    "lint": "eslint"
+    "lint": "eslint",
+    "api:types": "openapi-typescript http://localhost:8000/api/schema/ -o lib/api/schema.d.ts"
   },
 …
   "devDependencies": {
 …
     "eslint-config-next": "16.4.3",
+    "openapi-typescript": "^…",

```

`eslint.config.mjs`


El `^…` lo completa `npm install` con la versión actual.

`schema.d.ts` es código generado, igual que `next-env.d.ts`, que ya está en la lista. Si ESLint reportara algo ahí y lo corrigieras a mano, el próximo `npm run api:types` borraría la corrección. Por eso se excluye del lint.

El script usa la URL fija `localhost:8000`, como dice el roadmap, porque los scripts de npm no leen `.env.local`.

**Known uncertainty.** La API no estaba corriendo cuando se escribió este plan, así que no se revisó el schema generado. Los pasos 3, 6 y 8 asumen tres cosas:

1. **`paths` incluye `"/api/health/"`.** `HealthCheckView` es un `APIView` sin serializer, y drf-spectacular igual debería listarlo. Búscalo en `schema.d.ts`.
2. **Los enums se llaman `RegionEnum`, `StatusEnum` y `TypeEnum`**, dentro de `components["schemas"]`. drf-spectacular les agrega un sufijo cuando dos campos con el mismo nombre tienen opciones distintas, por ejemplo `Status3c5Enum`. Busca `Enum` en el archivo y anota los nombres reales.
3. **Tipos paginados:** drf-spectacular puede generar un tipo paginado por endpoint, como `PaginatedStoreList`. Igual creamos `Paginated<T>` en el paso 3, porque el roadmap lo pide para código genérico, como los controles de paginación.

**Verify:**
- `lib/api/schema.d.ts` existe, exporta `paths` y `components`, y contiene `"/api/health/"`.
- `npm run lint` pasa.
- `git status` muestra el archivo generado.

**Suggested commit name:** `chore: generate API types with openapi-typescript`

### Step 3 — Crear el cliente de la API y el tipo `Paginated<T>`

Todas las fases llaman a la API a través de un solo cliente, para no repetir la URL base, el header de autenticación ni el manejo de errores.

**El cliente es solo de servidor.** Lee `API_URL`, y desde la Fase 1 va a llevar el token del usuario. Si un Client Component lo importara, `process.env.API_URL` sería un string vacío en el navegador y la llamada saldría hacia una URL equivocada, sin ningún aviso. `import "server-only"` convierte ese error silencioso en un error de build ([Server and Client Components — Preventing environment poisoning](https://nextjs.org/docs/app/getting-started/server-and-client-components#preventing-environment-poisoning); local: `node_modules/next/dist/docs/01-app/01-getting-started/05-server-and-client-components.md`).

Ni `format.ts` ni `labels.ts` llevan ese import, porque los usarán Client Components: el formulario de movimientos de la Fase 3 y los gráficos de la Fase 5.

`openapi-fetch` y `server-only` se usan mientras la app atiende requests, así que van en `dependencies`. La documentación dice que en Next.js instalar `server-only` es opcional; lo instalamos para que la dependencia quede explícita.

**What we'll implement:**
- Instalar `openapi-fetch` y `server-only` como dependencias.
- Crear `lib/api/client.ts` con `createApiClient(accessToken?)`:
  - marcado `import "server-only"`;
  - lanza un error claro si `API_URL` falta o no es una URL válida;
  - devuelve un cliente `openapi-fetch` tipado con `paths`, con `baseUrl` igual a `API_URL` y el header `Authorization: Bearer <token>` cuando recibe un token.
- Crear `lib/api/types.ts` con `Paginated<T>` (`count`, `next`, `previous`, `results: T[]`).

```bash
npm install openapi-fetch server-only
```

`package.json`
```diff
   "dependencies": {
     "next": "16.4.3",
+    "openapi-fetch": "^…",
     "react": "19.3.0",
-    "react-dom": "19.3.0"
+    "react-dom": "19.3.0",
+    "server-only": "^…"
   },
```

`lib/api/client.ts` (nuevo)
```diff
+import "server-only";
+
+import createClient from "openapi-fetch";
+
+import type { paths } from "./schema";
+
+/**
+ * Creates a typed client for the Inventario API.
+ *
+ * Call it once per request and pass that request's access token (Phase 1).
+ * Never keep a token at module level: module scope is shared by every request.
+ */
+export function createApiClient(accessToken?: string) {
+  const apiUrl = process.env.API_URL;
+  if (!apiUrl) {
+    throw new Error("Falta la variable de entorno API_URL. Copia .env.example a .env.local.");
+  }
+  if (!URL.canParse(apiUrl)) {
+    throw new Error(`API_URL no es una URL válida: "${apiUrl}".`);
+  }
+
+  return createClient<paths>({
+    baseUrl: apiUrl,
+    headers: accessToken ? { Authorization: `Bearer ${accessToken}` } : {},
+  });
+}
```

`lib/api/types.ts` (nuevo)
```diff
+/** One page of a DRF list endpoint that uses PageNumberPagination. */
+export type Paginated<T> = {
+  count: number;
+  next: string | null;
+  previous: string | null;
+  results: T[];
+};
```

Qué notar:

- **Una función, no un cliente global, y es el error más peligroso de esta fase.** La tentación es `export const api = createClient(...)` más un `setAccessToken()`. Pero el código de un módulo se evalúa **una vez por proceso**, y sus variables las comparten todos los requests ([Caching — Predictable values](https://nextjs.org/docs/app/getting-started/caching#predictable-values); local: `node_modules/next/dist/docs/01-app/01-getting-started/08-caching.md`). Con un token guardado ahí, el request de un seller saldría con el token del último manager que inició sesión, y vería sus tiendas con sus permisos. El estado a nivel de módulo sirve solo para lo que es igual para todos, como los formateadores del paso 6.
- **La validación de `API_URL`.** Sin ella, `openapi-fetch` pegaría `undefined`/`""` con la ruta, quedaría la URL relativa `"/api/health/"`, y `fetch` lanzaría un `TypeError` en el servidor. Ese error es idéntico al de una API caída, y el desarrollador iría a revisar Django cuando el problema es su `.env.local`. El paso 8 explica por qué este error tiene que llegar a la página de error.
- **`Paginated<T>` es un tipo genérico:** `T` es un parámetro, como el de una función. `Paginated<Store>` tiene `results: Store[]` ([TypeScript Handbook — Generic Object Types](https://www.typescriptlang.org/docs/handbook/2/objects.html#generic-object-types); forma de la respuesta en [DRF — PageNumberPagination](https://www.django-rest-framework.org/api-guide/pagination/#pagenumberpagination)).
- **Fallas de `openapi-fetch`:**
  - Un 4xx o un 5xx **resuelve** con `{ data: undefined, error, response }` ([openapi-fetch — Response](https://openapi-ts.dev/openapi-fetch/#response)).
  - Una falla de red **lanza** el `TypeError` de `fetch`, porque `coreFetch` lo vuelve a lanzar si ningún middleware lo maneja ([openapi-fetch — Middleware](https://openapi-ts.dev/openapi-fetch/api#middleware)).

  Los pasos 7 y 8 se apoyan en esa diferencia.

**Verify:** `npm run lint` y `npm run build` pasan. Nadie usa todavía el cliente; el build revisa los tipos. Para confirmar la protección, puedes importar `createApiClient` desde un archivo con `"use client"` y ver que el build falla. Después borra esa prueba.

**Suggested commit name:** `feat: add server-only API client and Paginated type`

### Step 5 — Pasar el layout a español y montar el `<Toaster />`

El layout raíz envuelve todas las páginas y no se vuelve a montar al navegar ([Layouts and Pages](https://nextjs.org/docs/app/getting-started/layouts-and-pages); local: `node_modules/next/dist/docs/01-app/01-getting-started/03-layouts-and-pages.md`). Por eso tiene tres cosas que valen para toda la app:

- **El idioma.** `lang="en"` con contenido en español hace que un lector de pantalla lea con pronunciación inglesa, y que el navegador ofrezca traducir "del inglés" ([MDN — `lang`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/lang)).
- **El título.**
- **El `<Toaster />`.** Sonner solo muestra un `toast()` si hay un `<Toaster />` montado: *"it will be the place where all your toasts will be rendered"* ([README de sonner — Usage](https://github.com/emilkowalski/sonner#usage)). shadcn lo pone en `app/layout.tsx` ([shadcn/ui — Sonner](https://ui.shadcn.com/docs/components/radix/sonner)). En el layout, un aviso lanzado antes de un `redirect` sigue visible en la página siguiente. En `page.tsx`, en cambio, solo existiría en `/`.

**What we'll implement:**
- Cambiar `lang="en"` por `lang="es"`.
- Reemplazar la `metadata` de la plantilla:
  - un título con `default` "Simulador de Cadena de Tiendas" y `template` "%s | Simulador de Cadena de Tiendas";
  - una descripción en español.
- Montar `<Toaster theme="light" />` dentro del `<body>`, después de `{children}`.

`app/layout.tsx`
```diff
 import type { Metadata } from "next";
 import { Geist, Geist_Mono } from "next/font/google";
+
+import { Toaster } from "@/components/ui/sonner";

 …

-  title: "Create Next App",
-  description: "Generated by create next app",
+  title: {
+    default: "Simulador de Cadena de Tiendas",

   return (
```

Qué notar:

- **`template` necesita `default`.** `title.template` solo se aplica a los segmentos **hijos**, así que `title.default` es obligatorio: es el título de las páginas que no definen uno propio, como `/` ([generateMetadata — `template`](https://nextjs.org/docs/app/api-reference/functions/generate-metadata#template); local: `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/generate-metadata.md`). Desde la Fase 1, una página con `title: "Tiendas"` se verá como "Tiendas | Simulador de Cadena de Tiendas".
- **`theme="light"`.** El `sonner.tsx` de shadcn lee el tema con `useTheme()` de `next-themes`, y sin un `ThemeProvider` cae en `"system"`. Con un sistema operativo en modo oscuro, los avisos saldrían oscuros en una app que el roadmap define "Light theme only for now".
- **Un Client Component dentro de un layout de servidor.** `Toaster` es un Client Component (`"use client"` en `components/ui/sonner.tsx`), y un Server Component puede renderizarlo sin problema.

**Known uncertainty.** `theme="light"` solo funciona si el wrapper de shadcn esparce `{...props}` **después** de su propio `theme`. Así era al escribir este plan. Si el aviso sigue oscuro con el sistema en modo oscuro, cambia el valor por defecto dentro de `components/ui/sonner.tsx`.

**Verify:**
- En las DevTools, `<html lang="es">`.
- La pestaña dice "Simulador de Cadena de Tiendas".
- `npm run build` pasa.

**Suggested commit name:** `feat: switch root layout to Spanish and mount Toaster`

### Step 6 — Crear el formato `es-CL` y los nombres en español

Todas las pantallas muestran precios, cantidades, fechas y códigos de la API. Si cada página formateara por su cuenta, el mismo precio se vería distinto en dos pantallas, y un código como `temporarily_closed` terminaría en la UI.

**What we'll implement:**
- Crear `lib/format.ts`, todo con `Intl` y `es-CL`:
  - `formatCLP(amount)`: acepta `string | number`, porque DRF manda los decimales como string.
  - `formatNumber(value)`.
  - `formatDateTime(isoDateTime, timeZone)`: numérico, en la zona horaria que se le pasa.
  - `formatDate(isoDate)`: para fechas sin hora; formatea en UTC.
- Crear `lib/labels.ts`:
  - `regionNames`, `storeStatusNames`, `movementTypeNames` y `roleNames`, cada uno un `Record<Código, string>` que exige todos los códigos;
  - `spanishNameOrCode(names, code)`, que devuelve el código tal cual si no lo conoce.

`lib/format.ts` (nuevo)
```diff
+// Same for every request, so they are created once at module level.
+const clpFormatter = new Intl.NumberFormat("es-CL", { style: "currency", currency: "CLP" });
```

### Step 7 — Crear los helpers de errores de la API

Cada página y cada formulario de las fases siguientes recibe respuestas de error de la API. Si cada uno las interpretara a su manera, un 403 se vería distinto en cada pantalla, y algún formulario terminaría tragándose un error. Por eso hay dos helpers, uno para cada lugar donde se usan.

**Para páginas.** Un Server Component que recibió una respuesta no OK:
- un **404** muestra la página 404;
- un **403** muestra "No tienes permiso";
- cualquier otro status es inesperado y se lanza hacia `error.tsx`.

El 403 no se puede **lanzar**. En producción, un error que un Server Component reenvía a `error.tsx` llega con un mensaje genérico y un `digest`, no con su texto ([error.js — `error.message`](https://nextjs.org/docs/app/api-reference/file-conventions/error#errormessage); local: `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md`). Una subclase de `Error` tampoco sirve, porque pierde su clase al serializarse. Por eso el helper **devuelve** un elemento.

Se compararon dos formas de devolverlo, y se eligió la segunda:

| Forma | A favor | En contra |
|---|---|---|
| Devolver un string | `errors.ts` queda sin JSX | cada página decide cómo mostrarlo |
| **Devolver `<PermissionDenied />`** | cada página escribe una línea y el mensaje se ve igual en todas | el archivo pasa a `.tsx` y depende de un componente |

**Para formularios.** Una Server Action recibe la respuesta de error y la convierte en `{ formError, fieldErrors }`, el estado que el formulario muestra con `useActionState`.

Así funciona un formulario de las fases siguientes ([Forms](https://nextjs.org/docs/app/guides/forms); local: `node_modules/next/dist/docs/01-app/02-guides/forms.md`):

1. El `<form action={formAction}>` envía su `FormData` a una Server Action, que corre en el servidor.
2. La action **devuelve** un objeto.
3. `useActionState` lo guarda como `state` y vuelve a renderizar el formulario.
4. `pending` deshabilita el botón mientras tanto.

Los errores esperados se modelan como valores de retorno, no como `throw` ([Error Handling — Server Functions](https://nextjs.org/docs/app/getting-started/error-handling#server-functions); local: `node_modules/next/dist/docs/01-app/01-getting-started/10-error-handling.md`).

La regla del helper:

| En el cuerpo de DRF | Va a |
|---|---|
| `detail` | `formError` (arriba del formulario) |
| `non_field_errors` | `formError` |
| un campo que el formulario muestra | `fieldErrors[campo]` (debajo de su input) |
| un campo que el formulario **no** muestra | `formError`, con el nombre del campo delante |

Además:
- Si el valor es una lista, sus textos se unen en uno solo.
- Si no se pudo sacar ningún mensaje, `formError` recibe un mensaje genérico en español. Eso pasa cuando el cuerpo no es JSON, viene vacío o tiene una forma desconocida.

**What we'll implement:**
- Crear `components/permission-denied.tsx` con `PermissionDenied`: una `Card` que dice "No tienes permiso" y una línea de explicación.
- Crear `lib/api/errors.tsx` con:
  - el tipo `FormState<FieldName>`, con `formError: string | null` y `fieldErrors` (un mensaje por campo);
  - `renderApiErrorForPage(response)`:
    - 404 → `notFound()`;
    - 403 → devuelve `<PermissionDenied />`;
    - otro status → lanza un `Error`;
  - `formStateFromApiError(errorBody, displayedFieldNames)`, que aplica la regla de la tabla;
  - los helpers privados `isPlainObject`, `joinErrorMessages` e `isDisplayedFieldName`.

```diff
+import { notFound } from "next/navigation";
+import type { ReactElement } from "react";
+
+import { PermissionDenied } from "@/components/permission-denied";
+
+/** What a form built with useActionState shows after its Server Action fails. */
+export type FormState<FieldName extends string> = {
+  formError: string | null;
+  fieldErrors: Partial<Record<FieldName, string>>;
+};
+
+const genericFormErrorMessage = "No se pudo guardar. Revisa los datos e intenta de nuevo.";
+
+/**
+ * For Server Components, after checking `!response.ok`.
+ * Call it outside any try/catch: notFound() works by throwing, and a catch would swallow it.
+ */
+export function renderApiErrorForPage(response: Response): ReactElement {
+  if (response.status === 404) notFound();
+  if (response.status === 403) return <PermissionDenied />;
+  throw new Error(`La API respondió ${response.status}.`);
+}
+
+/**
+ * For Server Actions: turns a DRF error body into the state the form shows.
+ * Errors for fields the form doesn't display go to formError, so none is lost.
+ */
+export function formStateFromApiError<FieldName extends string>(
+  errorBody: unknown,
+  displayedFieldNames: readonly FieldName[],
+): FormState<FieldName> {
+  const formLevelMessages: string[] = [];
+  const fieldErrors: Partial<Record<FieldName, string>> = {};
+
+  if (isPlainObject(errorBody)) {
+    for (const [key, value] of Object.entries(errorBody)) {
+      const message = joinErrorMessages(value);
+      if (message === null) continue;
+
+      if (key === "detail" || key === "non_field_errors") {
+        formLevelMessages.push(message);
+      } else if (isDisplayedFieldName(key, displayedFieldNames)) {
+        fieldErrors[key] = message;
+      } else {
+        formLevelMessages.push(`${key}: ${message}`);
+      }
+    }
+  }
+
+  if (formLevelMessages.length === 0 && Object.keys(fieldErrors).length === 0) {
+    return { formError: genericFormErrorMessage, fieldErrors };
+  }
+  return {
+    formError: formLevelMessages.length > 0 ? formLevelMessages.join(" ") : null,
+    fieldErrors,
+  };
+}
+
+function isPlainObject(value: unknown): value is Record<string, unknown> {
+  return typeof value === "object" && value !== null && !Array.isArray(value);
+}
+
+// DRF sends a list of strings from validation (is_valid) and a plain string from create()/save().
+function joinErrorMessages(value: unknown): string | null {
+  if (typeof value === "string") return value;
+  if (Array.isArray(value)) {
+    const messages = value.filter((item): item is string => typeof item === "string");
+    return messages.length > 0 ? messages.join(" ") : null;
+  }
+  return null;
+}
+
+function isDisplayedFieldName<FieldName extends string>(
+  key: string,
+  displayedFieldNames: readonly FieldName[],
+): key is FieldName {
+  return (displayedFieldNames as readonly string[]).includes(key);
+}
```

- **La trampa de `notFound()` dentro de un `try`.** `notFound()` funciona **lanzando** una excepción ([notFound — Good to know](https://nextjs.org/docs/app/api-reference/functions/not-found#good-to-know); local: `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/not-found.md`). - **Los campos que el formulario no muestra.** Sin la lista de campos visibles, un error en un input oculto (`{"product": ["Invalid pk \"99\"…"]}`) iría a `fieldErrors.product`. - **`FormState<FieldName>` es genérico, como `Paginated<T>`.** Así, `state.fieldErrors.quantiy`, mal escrito, falla en el build.
- **El status HTTP del 403.** La página con `<PermissionDenied />` responde con status 200. Un 403 real necesitaría `forbidden()`, que es experimental, y el roadmap dice no usarlo.
- **El 401 no está aquí.** Lo agrega la Fase 1.
- **Mensajes de la API.** Los de `detail` llegan en inglés. El roadmap traduce los esperados en cada fase y deja el texto de la API como respaldo.

## What you learned

### `.gitignore` y la excepción `!`

**Question:** Si creas `.env.example` con el `.gitignore` de hoy y corres `git status`, ¿qué pasa?
**Answer:** No aparece, porque `.env*` también lo ignora (`*` calza con cualquier cosa salvo `/`). Se arregla con `!.env.example` **después** de `.env*`, porque gana el último patrón que calza. Reemplazar `.env*` por una lista de nombres dejaría sin cubrir variantes como `.env.production.local`.
**Source:** [gitignore — PATTERN FORMAT](https://git-scm.com/docs/gitignore#_pattern_format) y [DESCRIPTION](https://git-scm.com/docs/gitignore#_description); [Environment Variables — Load order](https://nextjs.org/docs/app/guides/environment-variables#environment-variable-load-order) (local: `node_modules/next/dist/docs/01-app/02-guides/environment-variables.md`).

### Cache Components y datos sin caché

**Question:** Con `cacheComponents: true`, si `page.tsx` hace `await` a `/api/health/` sin `<Suspense>` ni `loading.tsx`, ¿qué pasa en `npm run build`?
**Answer:** Falla el build. Next.js no puede generar el static shell de `/` y reporta un acceso sin caché fuera de un límite de `<Suspense>`.
**Source:** [Building — Prerender validation](https://nextjs.org/docs/app/guides/building#prerender-validation) (local: `node_modules/next/dist/docs/01-app/02-guides/building.md`).

### Static shell y streaming

**Question:** ¿Cómo armarías la portada para que el build pase y el estado de la API siempre esté fresco? ¿Qué queda dentro y fuera de `<Suspense>`, y qué va en el static shell?
**Answer:**
- Dentro de `<Suspense>`: la llamada a la API.
- Fuera: solo lo que no depende de datos sin caché. Algo dinámico afuera haría fallar el build.
- En el static shell: lo de afuera más el `fallback`. El resultado llega por streaming.
**Source:** [Caching — Streaming uncached data](https://nextjs.org/docs/app/getting-started/caching#streaming-uncached-data) (local: `node_modules/next/dist/docs/01-app/01-getting-started/08-caching.md`).

### Variables sin `NEXT_PUBLIC_` en el navegador

**Question:** Si un Client Component importa `client.ts` sin `server-only`, ¿qué vale `process.env.API_URL` en el navegador?
**Answer:** Un string vacío: Next.js reemplaza las variables sin prefijo. El código corre sin avisar, contra una URL equivocada, y `import "server-only"` lo convierte en un error de build.
**Source:** [Server and Client Components — Preventing environment poisoning](https://nextjs.org/docs/app/getting-started/server-and-client-components#preventing-environment-poisoning) (local: `node_modules/next/dist/docs/01-app/01-getting-started/05-server-and-client-components.md`).

### Qué módulos son solo de servidor

**Question:** De `api/client.ts`, `api/errors.ts`, `format.ts` y `labels.ts`, ¿cuáles llevan `import "server-only"`?
**Answer:** Solo `client.ts`, porque lee `API_URL` y llevará el token. `format.ts` y `labels.ts` los usarán Client Components: el formulario de la Fase 3 y los gráficos de la Fase 5.
**Source:** La misma sección de [Preventing environment poisoning](https://nextjs.org/docs/app/getting-started/server-and-client-components#preventing-environment-poisoning); `docs/roadmap.md`, fases 3 y 5.

### `openapi-fetch` ante un 4xx

**Question:** La API responde 404 con `{"detail": "…"}`. ¿Qué hace `await api.GET(...)`?
**Answer:** Resuelve: `data` queda `undefined`, `error` trae el cuerpo y `response.status` es 404. Un 4xx o un 5xx no lanzan.
**Source:** [openapi-fetch — Response](https://openapi-ts.dev/openapi-fetch/#response).

### `openapi-fetch` ante una falla de red

**Question:** Con Django apagado, ¿qué hace `api.GET("/api/health/")`, y qué implica para el componente?
**Answer:** Lanza el error de `fetch`, porque `coreFetch` lo vuelve a lanzar si ningún middleware lo maneja. El componente tiene que atraparlo para mostrar un mensaje en vez de caerse.
**Source:** [openapi-fetch — Middleware](https://openapi-ts.dev/openapi-fetch/api#middleware); `coreFetch` en [el código de openapi-fetch](https://github.com/openapi-ts/openapi-typescript/blob/main/packages/openapi-fetch/src/index.js).

### `error.message` en producción

**Question:** Si el helper hace `throw new Error("No tienes permiso")` y `error.tsx` muestra `error.message`, ¿qué se ve con `npm run build && npm start`?
**Answer:** Un mensaje genérico con un `digest`. Los errores que un Server Component reenvía se sanean para no filtrar detalles, y una subclase pierde su clase al serializarse. Por eso el 403 se renderiza, no se lanza.
**Source:** [error.js — `error.message`](https://nextjs.org/docs/app/api-reference/file-conventions/error#errormessage) (local: `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md`).

### `notFound()` dentro de un `try`

**Question:** Un componente llama a `notFound()` dentro de un `try` cuyo `catch` muestra "No se pudo conectar con la API". La tienda responde 404. ¿Qué ve el usuario?
**Answer:** El mensaje del `catch`, que es falso. `notFound()` lanza una excepción, y el primero que la atrapa es ese `catch`. El `try` debe envolver solo la llamada a la API.
**Source:** [notFound — Good to know](https://nextjs.org/docs/app/api-reference/functions/not-found#good-to-know) (local: `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/not-found.md`).

### Estado a nivel de módulo

**Question:** Si `client.ts` guarda el token en una variable del módulo y dos usuarios usan la app a la vez, ¿qué sale mal?
**Answer:** Hay una sola copia por proceso, compartida por todos los requests. El request de un seller sale con el token del último manager que inició sesión. El cliente se crea por request, con el token de quien lo llama.
**Source:** [Caching — Predictable values](https://nextjs.org/docs/app/getting-started/caching#predictable-values) (local: `node_modules/next/dist/docs/01-app/01-getting-started/08-caching.md`).

### Forma de los errores de DRF

**Question:** Un error lanzado en `validate()` y otro lanzado en `create()`, ¿tienen la misma forma en el JSON?
**Answer:** No:
- `validate()` corre en `is_valid()`, que pasa por `as_serializer_error` y envuelve el string en una lista: `{"quantity": ["…"]}`.
- `create()` corre en `save()`, nadie lo envuelve, y queda como string: `{"quantity": "…"}`.
**Source:** `as_serializer_error` y `run_validation` en [el `serializers.py` de DRF](https://raw.githubusercontent.com/encode/django-rest-framework/master/rest_framework/serializers.py); [DRF — Exceptions](https://www.django-rest-framework.org/api-guide/exceptions/#inspecting-api-exceptions).

### Decimales de DRF

**Question:** ¿Qué tipo de JSON llega en `Product.price` y en el `value` de las métricas?
**Answer:** Un string, como `"12990.00"`, porque `coerce_to_string` es `True` por defecto. `formatCLP` acepta `string`.
**Source:** [DRF — DecimalField](https://www.django-rest-framework.org/api-guide/fields/#decimalfield).

### `Record` exhaustivo

**Question:** ¿Cómo escribirías el objeto de nombres de regiones para que el build falle si falta una o si una clave está mal escrita?
**Answer:** `const regionNames: Record<RegionCode, string> = { … }`. TypeScript exige una propiedad por cada código y rechaza las que no existen, y el build revisa los tipos.
**Source:** [TypeScript — `Record<Keys, Type>`](https://www.typescriptlang.org/docs/handbook/utility-types.html#recordkeys-type).

### El helper de páginas

**Question:** Ante una respuesta no OK, ¿qué hace el helper con un 404, con un 403 y con el resto?
**Answer:**
- 404 → `notFound()`.
- 403 → devuelve algo que la página renderiza, porque no puede lanzarse.
- El resto → lanza hacia `error.tsx`.

Elegiste devolver `<PermissionDenied />` en vez de un string.
**Source:** [error.js — `error.message`](https://nextjs.org/docs/app/api-reference/file-conventions/error#errormessage); [notFound](https://nextjs.org/docs/app/api-reference/functions/not-found#good-to-know).

### Formularios con Server Actions y `useActionState`

**Question:** ¿Cómo funciona un formulario en Next.js?
**Answer:**
- El `<form action>` recibe una Server Action, que corre en el servidor y recibe el `FormData`.
- La action puede devolver un valor.
- `useActionState(action, initialState)`, en un Client Component, devuelve `[state, formAction, pending]`:
  - `state` es lo último que devolvió la action;
  - `pending` sirve para deshabilitar el botón.
- La action recibe `(prevState, formData)`.
- Los errores esperados se **devuelven**, no se lanzan.
**Source:** [Forms](https://nextjs.org/docs/app/guides/forms) (local: `node_modules/next/dist/docs/01-app/02-guides/forms.md`); [Error Handling — Server Functions](https://nextjs.org/docs/app/getting-started/error-handling#server-functions).

### `detail`, `non_field_errors` y campos

**Question:** ¿Dónde va cada cuerpo de DRF en `{ formError, fieldErrors }`?
**Answer:**
- `detail` → `formError`, porque no es de ningún campo.
- `non_field_errors` → `formError`, porque involucra todo el formulario o varios campos.
- `{"quantity": […]}` → `fieldErrors.quantity`, porque coincide con el `name` de un input.
**Source:** [DRF — Exceptions](https://www.django-rest-framework.org/api-guide/exceptions/#exception-handling-in-rest-framework-views); [DRF — `NON_FIELD_ERRORS_KEY`](https://www.django-rest-framework.org/api-guide/settings/#non_field_errors_key).

### Lista o string en un campo

**Question:** `{"quantity": "…"}` y `{"quantity": ["…"]}`: ¿qué diferencia hay y qué hace el helper?
**Answer:** Uno es un string, porque sale de `create()`; el otro una lista, porque sale de `validate()`. El helper une los textos de la lista y deja el string tal cual, así el formulario siempre recibe un solo texto.
**Source:** `as_serializer_error` en [el `serializers.py` de DRF](https://raw.githubusercontent.com/encode/django-rest-framework/master/rest_framework/serializers.py).

### `dependencies` y `devDependencies`

**Question:** ¿En qué sección va cada paquete: `openapi-fetch`, `openapi-typescript` y `server-only`?
**Answer:**
- `openapi-fetch` → `dependencies`, porque la app lo usa en cada request.
- `server-only` → `dependencies`, porque lo importa el código de la app.
- `openapi-typescript` → `devDependencies`, porque solo corre con `npm run api:types`.

El comando largo se guarda como script en `package.json`.
**Source:** [npm — package.json, devDependencies](https://docs.npmjs.com/cli/v10/configuring-npm/package-json#devdependencies).

**Source:** [MDN — `lang`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/lang).

### La página de inicio y `"use server"`

**Question:** ¿Cómo organizarías `page.tsx`? Y si no tuviera `"use server"`, ¿sería un componente de servidor o de cliente?

### Tipos genéricos

**Question:** ¿Cómo escribirías un solo tipo `Paginated` que sirva para `Paginated<Store>` y `Paginated<Product>`?
**Answer:** `type Paginated<T> = { count: number; next: string | null; previous: string | null; results: T[] }`. `T` es un parámetro de tipo, como el de una función.

### Qué puede salir mal en la página de inicio

**Question:** En el trayecto de `API_URL` al request, a Django y a la página, ¿qué puede salir mal, y qué recibe el código en cada caso?
**Answer:**

- Una API caída **lanza**.
- Una respuesta 500 **resuelve**.

### `try/catch` o `if`

**Question:** Para (a) Django apagado y (b) Django respondiendo 500, ¿`openapi-fetch` lanza o resuelve, y con qué lo detecta el componente?
**Answer:**
- (a) Lanza → `try/catch`.

### Falta `API_URL`

**Question:** Si alguien olvida `.env.local`, ¿qué mensaje ve, por qué engaña y qué cambiarías?
**Answer:**
- Ve "No se pudo conectar con la API", porque la URL relativa hace que `fetch` lance y cae en el `catch`.
- Engaña porque apunta a Django y no a la configuración.
- El cambio: `createApiClient` valida que `API_URL` exista y sea una URL, y lanza un error claro.
**Source:** [Environment Variables](https://nextjs.org/docs/app/guides/environment-variables) (local: `node_modules/next/dist/docs/01-app/02-guides/environment-variables.md`).

### El cliente fuera del `try`

**Question:** Si `createApiClient()` se llama dentro del `try`, ¿qué ve el desarrollador?
**Answer:** Otra vez "No se pudo conectar", porque el `catch` se traga el error de configuración. El cliente se crea fuera del `try`, para que el error llegue a la terminal y a la página de error.
**Source:** [Error Handling — Uncaught exceptions](https://nextjs.org/docs/app/getting-started/error-handling#handling-uncaught-exceptions).

### No filtrar detalles en el `catch`

**Question:** Si el `catch` muestra `error.cause`, ¿se ve la dirección interna de Django en producción? ¿Qué muestras y dónde dejas el detalle?
**Answer:**
- Sí se ve. La protección de Next.js solo se aplica a los errores que se reenvían a `error.js`, y aquí el texto lo pone nuestro JSX.
- `digest` no existe en un error atrapado.
- Al usuario, un mensaje fijo. El detalle, con `console.error`, que en un Server Component escribe en la terminal del servidor.
**Source:** [error.js — `error.message` y `error.digest`](https://nextjs.org/docs/app/api-reference/file-conventions/error#errormessage) (local: `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md`); [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components).

**Answer:** Nada, porque nadie renderiza `fieldErrors.product`. Es una falla silenciosa. Decidiste que el helper reciba los campos visibles y mande el resto a `formError`.
